# Open Payments Console Implementation Plan

> **For whoever executes this:** Follow [Delivery workflow](../../delivery-workflow.md). Tasks C1 and C2 belong to the design gate (Opus). Tasks C3-C13 are built by DeepSeek inside stages 1 and 2 ([D49](../../decisions.md#d49)), and each stage's independent review by Opus in a fresh session covers its tasks. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Build a responsive web console that lets the business running Open Payments find any payment, understand it, and act on it without risking a double charge or double refund.

**Architecture:** `OpenPayments.Console` is a separate ASP.NET Core Razor Pages service with htmx. It reads from a replica, moves money only through the payment API, and writes staff and audit rows to its own schema. `REVIEW` resolution is the one new money path, and it lives in `OpenPayments.Transitions` behind an internal API route.

**Tech Stack:** .NET 10, ASP.NET Core Razor Pages, OpenID Connect, htmx (self-hosted), Npgsql, PostgreSQL 18, IBM Plex (self-hosted), xUnit, Testcontainers, `Microsoft.AspNetCore.Mvc.Testing`, Playwright with axe-core.

**Spec:** [Console design](../specs/2026-11-05-console-design.md). Decisions [D40-D45](../../decisions.md#d40). Gate record: [Stage C design](../../gates/stage-c-design.md).

**Task numbers show the design order, not the build order.** Stage 1 builds C4 and C6-C11, then C13. C4's migration includes `review_resolutions` for later use, so C5 and C12 add no schema.

**Stage 2 also builds:** the timer job that issues the escalation commands from Task C3, and the reconciler data for "last inquiry". The console works without them. Payments past the age limit appear in the queue, and they can't be resolved until they have been escalated.

## Global Constraints

- All [Stage 1 Global Constraints](2026-11-05-open-payments-implementation-and-benchmark.md#global-constraints) apply: commit and push to `main` with explicit paths, the author `EganNguyen <tuannh2y@gmail.com>`, no changes to `docs/decisions.md`, the spec or the API contract, warnings as errors, and money as minor units with a currency.
- Progress lines and escalations go in the records of the stage building the task.
- `OpenPayments.Console` must not reference `OpenPayments.Transitions`, and its database roles can't write money tables ([D2](../../decisions.md#d2), [D40](../../decisions.md#d40)).
- Self-hosted assets only. Pages make no request to any other origin, including fonts and scripts.
- Use `Microsoft.AspNetCore.Authentication.OpenIdConnect`. No password storage and no client-side token storage.
- Server checks every role on every request. Hiding a control is never the check.
- List range: default 7 days, maximum 31 days. Re-authentication window: 5 minutes. Replica lag banner: above 60 seconds. Authorization-expiry warning: 24 hours. Audit intent limit: 10 minutes. All are configuration with these defaults.
- Visual tokens, status rules, touch targets and motion limits come from the spec's [Visual design](../specs/2026-11-05-console-design.md#visual-design). Labels, tones and wording come from its [Actions by state](../specs/2026-11-05-console-design.md#actions-by-state), verbatim.
- Staff can't start a new attempt, and `UNKNOWN` never offers a retry.
- Check each new dependency's license and .NET 10 support first (S6).

## Review Focus

Likely to bite and not named by the spec's tests. Each has a test in the task shown.

1. **A staff member's session or role is removed while they have a form open.** Submitting must fail on the server with no API call (Task C6).
2. **Two people propose on the same case, or one approves as the other proposes.** Only one open proposal can exist, and only one approval can apply (Tasks C4, C5, C12).
3. **A currency with zero or three decimals.** Amounts display and parse correctly, such as JPY and KWD, and a refund form can't turn `10.50` into the wrong minor units (Task C7).
4. **Text from outside shown in a page.** A `failure_code`, an evidence note or a reason containing HTML must render as text (Tasks C9, C12).
5. **A phone resubmits a form after coming back online.** Same key, one action, and the page shows the real result (Task C11).

### Task C3: Escalation and manual resolution in `Decide`

**Files:**
- Modify: `src/OpenPayments.Domain/Commands.cs`, `States.cs`, `Decide.cs`
- Modify: `tests/OpenPayments.Domain.Tests/lifecycle-transitions.csv`, changing trigger text only, because no new state pairs are needed

**Interfaces:**
- Consumes: `PaymentRules.Decide`, `PaymentSnapshot`, `Posting`.
- Produces:
  - `PaymentCommand.Escalate(AttemptId AttemptId, AttemptOperation Operation, DateTimeOffset OccurredAt)`
  - `PaymentCommand.RefundEscalate(RefundId RefundId, DateTimeOffset OccurredAt)`
  - `PaymentCommand.ManualRefundResolution(RefundId RefundId, RefundResolution Resolution, DateTimeOffset OccurredAt)`
  - `PaymentCommand.LateApprovalReversed(AttemptId AttemptId, DateTimeOffset OccurredAt)`
  - `enum RefundResolution { Confirm, Release }`

**The rules:**

| Command | Allowed from | Result |
|---|---|---|
| `Escalate`, authorize or sale | Payment and attempt `UNKNOWN` | Both `REVIEW`, no ledger |
| `Escalate`, capture | Payment `AUTHORIZED`, attempt `UNKNOWN` | Both `REVIEW`, no ledger |
| `Escalate`, void | Any | Rejected `invalid_operation`. Stuck voids stay visible, unresolved |
| `RefundEscalate` | Refund `UNKNOWN` | Refund `REVIEW`, payment unchanged, amount stays reserved |
| `ManualResolution` | Payment `REVIEW` | Existing state and ledger behavior, plus the attempt change below |
| `ManualRefundResolution` | Refund `REVIEW` | `Confirm` posts as `RefundConfirm` does; `Release` posts as `RefundRelease` does |
| `LateApprovalReversed` | Sale attempt `REVIEW` | Attempt `FAILED` with `late_approval_reversed`, no ledger entry. Payment in `REVIEW` returns to `AWAITING_METHOD`; otherwise it's unchanged |

**Attempt change on `ManualResolution`,** which today leaves the attempt in `REVIEW`:

| Attempt operation | `Authorize` | `AwaitingMethod` | `Capture` |
|---|---|---|---|
| Authorize | `SUCCEEDED` | `FAILED` | `SUCCEEDED` |
| Sale | Rejected `invalid_resolution` | `FAILED` | `SUCCEEDED` |
| Capture | `FAILED` | Rejected `invalid_resolution` | `SUCCEEDED` |

A failed attempt gets the failure code `manual_resolution`.

**Interfaces:**

### Task C5: Applying a resolution, and the internal route

**Files:**
- Create: `src/OpenPayments.Transitions/ResolutionStore.cs`, `src/OpenPayments.Api/Endpoints/Internal.cs`
- Test: `tests/OpenPayments.Integration.Tests/ResolutionStoreTests.cs`, `tests/OpenPayments.Acceptance.Tests/InternalRouteTests.cs`

**Interfaces:**
- Consumes: commands from C3, tables from C4, `TxRunner.RunAsync`, the same in-transaction apply path `PaymentStore.ApplyAsync` uses.
- Produces:
  - `ResolutionStore.ApplyApprovedAsync(Guid resolutionId, Guid approverStaffId, DateTimeOffset now, CancellationToken ct) -> Task<ResolutionResult>`
  - `ResolutionResult`: `Applied(PaymentView)`, `AlreadyApplied(PaymentView)`, `SelfApproval`, `NotProposed`, `StateChanged(PaymentView)`
  - Route `POST /internal/v1/resolutions/{id}/apply`, body `{ "approver_staff_id": uuid }`. Answers 200, 409 with a reason code, or 403 for self-approval.

**How it works:** in one transaction, lock the `review_resolutions` row, check it's `proposed` and that the approver differs, map its kind and outcome to a C3 command, run `Decide`, write state, ledger and outbox as usual, set the row to `applied`, and insert an `event` audit row. This rare path needs three statements beyond the five-statement guideline, which is accepted because the row lock serializes it per case and it isn't on the payment path.

The route requires a key with the scope `console:resolve`, is registered only when `Internal:Enabled` is true, and doesn't appear in `api/openapi.yaml`.
